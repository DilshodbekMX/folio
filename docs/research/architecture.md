# AREA: Overleaf Community Edition architecture and the CLSI compile service (with verified recommendations for a single-node clone)

I read the Overleaf source (github.com/overleaf/overleaf at commit e039ad26, 2026-09-17, shallow-cloned into the scratchpad). I also read the last public DockerRunner.js (commit 5140fff). It was removed from the public repo on 2026-01-22 in commit 645ee30, together with seccomp/clsi-profile.json, so sandboxed compiles are now Server Pro only. Community Edition (CE) today runs latexmk directly inside the single sharelatex container through LocalCommandRunner, which has no sandbox and no timeout. It even logs 'timeouts and sandboxing are not enabled with CommandRunner'. The system LatexMk file in CE contains only `$go_mode = 3;`. The CLSI command is fixed: `latexmk -cd -jobname=output -auxdir=$COMPILE_DIR -outdir=$COMPILE_DIR -synctex=1 -interaction=batchmode -time (-halt-on-error|-f) [flags e.g. -file-line-error] (-pdf|-xelatex|-lualatex|-pdfdvi) $COMPILE_DIR/<root>`. Other behaviours:
- Draft mode prepends `\PassOptionsToPackage{draft}{graphicx}\PassOptionsToPackage{draft}{graphics}` to line 1 of the root file inside the compile dir.
- Aux files are kept between compiles; output.pdf/log/synctex.gz/xdv are deleted before each run.
- Each build's files are copied into output/<project>/generated-files/<buildId>, where buildId = hex(Date.now())-hex(8 random bytes). Nginx serves them directly by build id.
- There is one in-memory lock per compile dir. A second compile gets 423 'compile-in-progress'.
- SyncTeX runs `synctex view -i line:col:/compile/file -o /compile/output.pdf` and `synctex edit -o page:h:v:/compile/output.pdf` in a read-only sandbox. Coordinates are PDF big points with the origin at the top-left of the page.

The edit path is ShareJS text OT: browser → real-time (socket.io 0.9 fork) → Redis `PendingProjectUpdates:{pid}` plus the `pending-updates-list` marker → document-updater. The document-updater transforms each op against `DocOps:{doc}`, which keeps the last 100 ops for 1 hour. It then publishes to the `applied-ops` pub/sub channel and flushes to Mongo via web and docstore after 5 minutes unflushed, or when the last user leaves. Ops also go to `ProjectHistory:Ops:{pid}` → project-history → history-v1. history-v1 stores immutable chunks (a snapshot plus up to 2000 changes or 5 MB) in Postgres/Mongo plus object storage, and git-SHA1 blobs. Labels live in Mongo `projectHistoryLabels`.

I checked the key claims against the local texlive/texlive:latest image (TeX Live 2026, latexmk 4.88, SyncTeX 1.5; `latest` has the same digest as `latest-full`):
- **Sandbox flags work.** The Overleaf-style command runs under `--network none --cap-drop ALL --security-opt no-new-privileges --read-only --tmpfs /tmp --user 1000:1000`.
- **`-gt` is needed to force a run.** It is what `$go_mode=3` means. Without it, an unchanged recompile is a no-op.
- **Error modes.** `-f` still produces a PDF on errors; `-halt-on-error` produces none. latexmk exits 12 in both cases.
- **`docker run` overhead** is about 250 ms, against about 45 ms for `docker exec`.
- **Killing a `docker exec` client leaves the process running** inside the container.
- **GNU `timeout` as the container's first process (PID 1) fails** silently with exit 125. `--init` fixes it.
- **RLIMIT_CPU is per process.** latexmk -f simply starts the next pass, so it is only a backstop behind a wall-clock timeout.
- **Draft mode works via `latexmk -usepretex=...`** without editing the source.
- **The user's paper.** antiddos_v2.tex with XeLaTeX takes 9.8 s cold (3 passes). With aux kept and a warm font cache, one pass takes about 1.8 s. It needs a persistent XDG_CACHE_HOME/TEXMFVAR volume.
- **The paper breaks with `-jobname=output`.** Its mutual xr `\externaldocument` links to the supplement need `<basename>.aux` files. With jobname = the file's basename in a shared compile dir, I confirmed 0 undefined references.

For the clone I recommend the following:
- A CompileRunner that runs one `docker run --rm --init` per compile, with a per-project single-flight lock that queues one follow-up run instead of refusing, and a global concurrency limit.
- A persistent compile dir per project (aux kept), and immutable per-build output dirs with the newest 3 kept and a 90-minute age limit.
- A persistent, pre-warmed TeX font cache volume.
- Deleting symlinks before each file sync and never following them when copying outputs. Our Node process runs on the host, not in a container like CLSI.
- Yjs instead of OT. Before compiling, check the client's Yjs state vector against the server's copy, to mirror Overleaf's awaitBufferedOps.

## [must] Stop on first error vs try despite errors (verified behaviour and status mapping)
stopOnFirstError => '-halt-on-error'; default => '-f'. Verified with an \undefinedmacro doc: '-f' => 2 pdflatex passes, 'Latexmk: Errors, in force_mode: so I tried finishing targets', output.pdf produced, exit code 12; '-halt-on-error' => 1 pass, 'Latexmk: Errors, so I did not complete making targets', NO output.pdf, exit code 12. CLSI therefore ignores the exit code (except 1 = chktex 'exited', 137 = killed) and derives status from outputs: status='success' if outputFiles has output.pdf with size>0; else 'stopped-on-first-error' if request.stopOnFirstError; else 'failure'. Frontend (output-files.ts) hides warnings matching /^(Reference|Citation).+undefined on input line/ when status is 'stopped-on-first-error' (they may vanish after another pass). Overleaf docs: after a manual stop in -f mode, next compile may show '! File ended while scanning use of \@writefile' from truncated aux — which is why CLSI wipes the compile dir after terminated/timedout compiles.

## [must] Draft (Fast) mode implementation + cleaner clone alternative (verified)
Overleaf DraftModeManager: PREFIX = '\\PassOptionsToPackage{draft}{graphicx}\\PassOptionsToPackage{draft}{graphics}' is prepended to the root file IN THE COMPILE DIR ONLY (writeFile(PREFIX + content)), with no newline so all line numbers (errors, SyncTeX) stay valid. ## [must] Timeout layers in Overleaf

## [must] Concurrency and locking in CLSI + web
CLSI LockManager: in-process Map keyed by compileDir; acquire() throws AlreadyCompilingError (→ HTTP 423, status 'compile-in-progress') if a non-expired lock exists, releases expired ones with a warning; then checkConcurrencyLimit: if LOCKS.size > Settings.compileConcurrencyLimit (64, or 32 on spot instances) → TooManyCompileRequestsError → 503 'unavailable' (web retries once with syncType full on a new server). Lock has waitForRelease() promise used by stopCompile: kill + await release. Word count sync also takes the same lock. OutputCacheManager.queueDirOperation(dir, fn) serialises all output-dir mutations (save build, expiry, synctex) per project via a promise chain in a Map (pending.then(fn, fn).finally(delete-if-last)). Compile dir name is `${projectId}` or `${projectId}-${userId}` (per-user compiles default on; Settings.disablePerUserCompiles turns off) so collaborators never block each other. isInitialCompile detected via `(await fs.mkdir(dir,{recursive:true})) === dir`. web: CompileManager._checkIfRecentlyCompiled: redis SET compile:{pid}:{uid} true EX 1 NX → 'too-recently-compiled'; auto-compiles consume RateLimiter('auto-compile:<group>', points 25 default, duration 20 s) → 'autocompile-backoff'. Frontend: compilingRef prevents overlapping requests; if an auto-compile arrives while compiling it re-arms the debounce.

## [should] Resource sync to the compile dir (full vs incremental) and path safety
Full sync: mkdir compile dir, _removeExtraneousFiles, write every resource (content → fs.writeFile; url → UrlCache.downloadUrlToFile, cache key = URL pathname with '/'→'-' + '-' + modified.getTime(), stored under cache/<pid>/ and copied in; download failures are logged and compile continues), then write `.project-sync-state` = resource paths joined by '\n' + final line `stateHash:<syncState>` (max read 128 KiB). Incremental sync: stateHash must equal stored one else FilesOutOfSyncError (409); all listed paths must still exist; only changed docs are (re)written, binaries untouched. Path check (ResourceWriter.checkPath): path = normalize(join(base, rel)); reject unless path.startsWith(base + '/'). rootResourcePath and syncState list reject any '..' segment. For our clone: keep a JSON sync state {stateHash, files: {path: sha256}} and only rewrite files whose hash changed (preserves mtimes, keeps latexmk's fdb happy).

## [must] Incremental compile: which generated files are kept vs deleted between compiles
Before each compile, every non-resource file in the compile dir is classified by ResourceWriter.isExtraneousFile(path). KEEP: /^output\./, /\.aux$/, /^cache\// (knitr), /^output-.*/ and /\.(pdf|dpth|md5)$/ (TikZ externalize caches), /\.(pygtex|pygstyle)$/ and /(^|\/)_minted(-[^\/]+)?\// (minted), /\.md\.tex$/ and /(^|\/)_markdown_[^\/]+\// (markdown pkg), /-eps-converted-to\.pdf$/ (epstopdf), plus Settings.preciousFilePattern (minimatch, dot:true). ALWAYS DELETE (overrides keep): output.tar.gz, output.synctex.gz, output.pdfxref, output.pdf, output.dvi, output.log, output.xdv, output.stdout, output.stderr, output.tex. Everything else not in the resource list (stale user files, removed docs) is deleted (files only, not dirs). So output.aux/.bbl/.blg/.toc/.out/.fls/.fdb_latexmk/.bcf/.run.xml and chapter .aux survive → subsequent compiles usually need 1 pass. ## [must] Output files: build ids, naming, copy, response
generateBuildId = `${Date.now().toString(16)}-${crypto.randomBytes(8).toString('hex')}` (web now generates it before fetching content and passes options.buildId; CLSI validates BUILD_REGEX /^[0-9a-f]+-[0-9a-f]+$/). ## [must] docker run --rm per compile vs persistent container + docker exec (measured)
Measured on this box: `docker run --rm --init ... true` ≈ 250-270 ms; `docker exec <c> true` ≈ 42-48 ms; a real XeLaTeX compile was 3.6 s (run) vs 3.4 s (exec), i.e. overhead is noise compared with TeX time. Critical gotchas found: (1) killing the `docker exec` CLI client (kill -9) does NOT kill the process inside the container — verified `sleep 300` kept running — so timeouts/stop with exec need an in-container `timeout -s KILL` plus `docker exec <c> pkill -KILL -u <uid>` or a container restart; (2) GNU `timeout` as the container's PID 1 fails silently with exit 125 — add `--init` (tini) or wrap in `sh -c`; (3) a shared persistent container shares memory/pids limits across projects and mounts every project → weak isolation. `docker kill olc-<pid>` on a `docker run --rm` compile returned in 82 ms with client exit code 137. Recommendation: `docker run --rm --init` per compile (one container per project at a time thanks to the project lock, name `olc-<projectId>`), kill via `docker kill`; use a single long-lived read-only 'tools' container (`sleep infinity`, network none, output root mounted :ro) only for latency-sensitive read-only commands (synctex, texcount) via docker exec. Overleaf's own middle ground (per-project container re-`start`ed, hourly GC) is not worth the complexity here.

## [must] OT vs Yjs for our clone, and how to mirror 'compile sees latest edits'
Overleaf keeps server-ordered OT because history-v1, tracked changes (ranges) and its multi-node Redis design depend on a single linear version per doc. For a single-node clone Yjs (CRDT) is simpler: no central transform, offline editing, awareness for cursors, y-codemirror.next binding. Costs: tombstone growth (keep gc on), CRDT versions don't map to linear history (take text snapshots into git instead), tracked changes/comments need Y.RelativePosition anchors. Mirror Overleaf's awaitBufferedOps: the client sends base64(Y.encodeStateVector(ydoc)) with each compile request; the server decodes it (Y.decodeStateVector → Map<clientID, clock>) and waits (≤10 s, like PENDING_OP_MAX_WAIT) until its server-side doc's state vector dominates it, then snapshots Y.Text.toString() for every doc into the compile dir. Only docs changed since the last sync are rewritten (the equivalent of 'incremental'); a changed file tree, or changed draft/engine options, triggers a full resync (the equivalent of the state-hash mismatch). Version pins as of 2026-09-21: yjs 13.6.32 (latest; 14.0.0-x is beta/next), y-protocols 1.0.7, y-codemirror.next 0.3.6 (peer yjs ^13.5.6), y-websocket 3.1.0 (client only; the server moved out). @y/websocket-server 0.1.2 and later depend on yjs ^14.0.0-7 and @y/protocols, which would load two Yjs copies. Either pin @y/websocket-server@0.1.1 (peer yjs ^13.5.6), or write the ~150-line sync/awareness server on ws 8.21.3 with y-protocols, which also gives you auth and persistence hooks.

## [must] Host-side symlink attacks (our Node runs on the host, unlike CLSI)
With shell escape (or even \openout into subdirs plus a latexmkrc), a compile can plant symlinks in /compile (e.g. `main.tex -> /home/you/.bashrc` or `figures -> /home/you`). CLSI mostly avoids this: OutputFileFinder only publishes dirent.isFile() entries, nginx has `disable_symlinks on`, and CLSI itself runs in a container. But ResourceWriter still does fs.writeFile(path) (follows symlinks) and a plain fs.copyFile would follow them too. In our clone the Node process is the host user, so: (1) before each sync walk the compile dir with fs.lstat / readdir withFileTypes and unlink every symlink (and anything not a regular file or dir); (2) write resources atomically: write to `${path}.olc-tmp-${rand}` then fs.rename over the target (rename replaces a symlink rather than following it) after checking that each parent component is a real directory (lstat); (3) when collecting outputs, include only lstat().isFile() entries and skip dot-files; (4) serve builds with express.static/send and `dotfiles: 'deny'`, only from builds/<validated buildId>/, with a path.normalize + startsWith(base + '/') check (Overleaf's checkPath rule). Also keep the container user unprivileged (--user uid:gid, cap-drop ALL, no-new-privileges) so it cannot chown or escalate.

## [should] Distinguishing kill reasons and exit codes
Verified codes: latexmk returns 12 when any rule failed (both -f and -halt-on-error), 0 on success; an engine killed by RLIMIT_CPU shows up in latexmk stdout as 'gave return code 152' (128+SIGXCPU 24); `docker kill` gives client exit 137; `docker run` itself failing (bad flag or image) gives 125. Classification order in the runner: our timeout fired ⇒ 'timedout'; our stop() fired ⇒ 'terminated'; exit 137 with neither ⇒ 'oom' (memory cgroup; with --rm there is no `docker inspect .State.OOMKilled`, so omit --rm and do `docker inspect -f '{{.State.OOMKilled}}' olc-<pid>; docker rm olc-<pid>` if you need certainty); exit 125/126/127 ⇒ 'error' (infrastructure); otherwise decide by the PDF (see the stop-on-first-error finding). Overleaf's clsi-nginx also logs an error if a 'core' file appears in the outputs, which catches segfaults such as the luaotfload one reproduced above.

## [should] docker CLI via spawn vs dockerode
Overleaf's CLSI pins dockerode ^4.0.9 and express 4.22.1. dockerode latest is 5.0.1 (Apache-2.0, 2026-06-24). 5.0.0 (2026-04-23) only dropped the uuid dependency and raised the minimum Node version, so the API is unchanged: getContainer(name).kill/wait/inspect/remove, createContainer(opts), container.attach({stream,stdout,stderr}) plus modem.demuxStream. @types/dockerode latest is 4.0.1. Switch to dockerode only if you need OOMKilled inspection without the CLI, or to talk to a remote Docker socket.

## Risks
- AGPL: Overleaf's CLSI, DockerRunner, log parser and linter are AGPL-3.0. Reimplement from the behaviour described here; do not copy code. DockerRunner is no longer in the public repo anyway: it was removed on 2026-01-22 and is Server Pro only.
- Host-side symlink exfiltration: our Node process runs on the host with the same uid as the container user. Symlinks created by a compile (shell escape, latexmkrc) could make a naive fs.writeFile or fs.copyFile read or overwrite host files. Unlink symlinks before each sync, write via rename, and publish only lstat().isFile() outputs.
- Killing a `docker exec` client does not kill the process in the container (verified). If you use exec anywhere, enforce timeouts inside the container and kill explicitly.
- GNU `timeout` as the container's first process (PID 1) exits 125 silently (verified). Always pass --init when wrapping commands.
- RLIMIT_CPU (--ulimit cpu) is per process. With latexmk -f, a looping document gets several passes of the limit each (verified 10.4 s with a 5 s soft limit). A Node-side wall-clock timeout plus `docker kill` is mandatory.
- The user's paper uses mutual xr \externaldocument between antiddos_v2 and antiddos_v2_supplementary. Overleaf's fixed -jobname=output breaks it. Use jobname = the root file's basename in a shared compile dir (verified: 0 undefined references).
- A cold font cache makes XeLaTeX passes about 2.5x slower. A first LuaLaTeX run with an empty TEXMFVAR segfaulted while building the luaotfload font database. Pre-warm a persistent cache volume (luaotfload-tool -u; fc-cache). A shared writable cache is a cross-project tampering vector if the server is ever multi-tenant.
- texlive/texlive:latest is a moving tag, 5.65 GB locally. Pin the digest so a TL2027 rollover doesn't change outputs silently; record the image digest in build meta.json.
- Enabling -shell-escape widens the attack surface. Keep it off by default (restricted mode already covers repstopdf/epstopdf for the MDPI .eps logos and latexminted), and only allow it with network none, a read-only root, pids and memory limits, cap-drop ALL and no-new-privileges.
- Coalescing concurrent compiles in one per-project compile dir means collaborators share the options (draft, stop-on-first-error). Include the options in the sync state so a change forces a clean resync. Otherwise the draft prefix or stale aux from a different engine can leak between compiles.
- Yjs ecosystem split: @y/websocket-server 0.1.2+ pulls yjs 14 prereleases. Mixing it with yjs 13.6.x and y-codemirror.next loads two Yjs copies and breaks sync. Pin versions or write the ws sync server yourself.
- Deleting output.pdf/log before each run (the Overleaf approach) means a failed or killed compile leaves the preview without a PDF unless the previous build dir is kept. Retention must always keep the last successful build.
